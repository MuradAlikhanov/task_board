# Task Board — Архитектура

> Приложение к `VISION.md`. Уровень: архитектурный обзор (стек, компоненты, взаимодействие, деплой). Без полных SQL-DDL и JSON-контрактов — они в `DATA_MODEL.md` и `API.md`.

---

## 1. Принципы архитектуры

1. **Файлы — источник правды, SQLite — индекс.** Все данные живут как Markdown + YAML в vault; SQLite-индекс пересобирается из файлов. Противоречие (см. VISION §9.2) — индекс всегда можно пересобрать.
2. **Obsidian-first.** Vault открыт и редактируем в Obsidian; система лишь надстройка для командной работы и быстрого UI.
3. **Компактность.** Малая команда → минимум сервисов, единая БД, простой деплой через docker compose.
4. **AI-ready.** Архитектура учитывает подключение ИИ-агентов (API по ключам, RAG).
5. **Изоляция.** Проектный vault отделён от личного (отдельная папка Syncthing).

### 3.1 Caddy (реверс-прокси / TLS)
- Терминирует HTTPS с автосертификатами Let's Encrypt.
- Маршрутизирует: `/` → Next.js, `/api/*` → FastAPI, `/bot/*` (webhook) → aiogram.
- Проксирует WebApp TMA.

### 3.2 Next.js (фронтенд: веб + TMA)
- Один кодбейз для десктопа и Telegram Mini App (адаптивная вёрстка).
- Получает данные через REST API FastAPI.
- TMA: авторизация через `Telegram.WebApp.initData` (проксируется на бэк для валидации).

### 3.3 FastAPI + aiogram Bot (один контейнер)
- **REST API** для заявок, проектов, контактов, wiki, отчётов, настроек (`API.md`).
- **Авторизация**: Telegram Login (веб), `initData` (TMA), API Keys (ИИ-агенты) (`API.md` §3).
- **Vault Watcher + Indexer**: подписка на изменения файлов vault (watchdog), парсинг frontmatter, обновление SQLite-индекса; запись изменений из UI обратно в `.md`.
- **aiogram-бот запускается как asyncio-таска** в том же процессе FastAPI (см. §10, решение по Q-A1). Получение апдейтов — **гибрид webhook/polling** (см. §10, Q-A4): в проде на VPS Caddy проксирует `/bot/webhook` на тот же процесс; при локальной разработке бот сам опрашивает Telegram (polling). Переключатель — `BOT_MODE=webhook|polling`.
- **События → уведомления**: доменная логика публикует события в **in-memory `asyncio.Queue`**; бот-таска читает очередь и отправляет в Telegram (общий чат + личные подписки, `§7.1` VISION). Внешняя очередь (Redis) не нужна.
- Команды `/task`, голос → Gemini (транскрипция) → создание заявки.

**Кодовая структура (модульное разделение под будущее разделение):**
```
backend/app/
  api/          # FastAPI-роутеры
  bot/          # aiogram: хендлеры, webhook
  domain/       # общая доменная логика (заявки, контакты, ...)
  events/       # шина событий (asyncio.Queue)
  indexer/      # vault watcher + SQLite-индексатор
  workers/      # background-задачи (I/O-bound + run_in_executor для CPU)
```
Модульность позволяет в будущем вынести бота/воркеры в отдельные контейнеры без переписывания.

### 3.4 Vault + SQLite-индекс (+ векторы)
- **Vault** (`/vault`): `.md`-файлы + `attachments/` — источник правды.
- **SQLite-индекс** (`.taskboard/index.sqlite`): таблицы заявок, контактов, проектов, **FTS5** для текстового поиска и **векторная таблица (sqlite-vec)** для семантического поиска.
- **Embedding**: считается через **Gemini API** при индексации wiki-страниц (помеченных `rag: true`, §6.1) и при поисковом запросе. Векторы (768-dim) хранятся в той же `index.sqlite`.
- Состав индекса пересобирается при изменении wiki; потеря index.sqlite не страшна (пересобирается из vault + Gemini).

### 3.5 Background-задачи (воркеры)
Долгая работа выносится из HTTP-запроса/бота, чтобы не блокировать их и не подвешивать event loop. Подход — гибрид (решение по Q-A5, §10):

| Тип задачи | Механизм | Примеры |
|------------|----------|---------|
| **I/O-bound** | `BackgroundTasks` FastAPI (в event loop) | вызовы Gemini API (embedding, транскрипция), рассылка Telegram, переиндексация vault, очистка осиротевших вложений |
| **CPU-bound** | `run_in_executor` (thread pool) | генерация PDF-отчётов |

Почему так — см. §10 (Q-A5). Ключевое: **ноль внешних зависимостей** (без Redis/Celery), единый писатель SQLite, консистентно с одним контейнером (Q-A1). Модульная структура кода (`app/workers/`) оставляет дверь открытой для выделения worker-контейнера в будущем.

## 4. Синхронизация vault ↔ индекс (ключевая механика)

```
     ┌─────────────────────────────────────────────────────┐
     │                 ИСТОЧНИК ПРАВДЫ                     │
     │          vault/*.md + attachments/                  │
     └──────────────┬───────────────────┬──────────────────┘
                    │                   │
       (1) file watcher       (2) запись из UI
       (изменение в Obsidian/     (правка в веб/TMA)
        Syncthing)
                    ▼                   ▼
     ┌─────────────────────────────────────────────────────┐
     │              Vault Watcher + Indexer                │
     │ parse frontmatter → нормализация → валидация        │
     └──────────────┬───────────────────┬──────────────────┘
                    ▼                   ▲
     ┌─────────────────────────────────────────────────────┐
     │               SQLite-индекс (FTS5)                  │
     │    пересобирается из файлов при рассинхроне         │
     └─────────────────────────────────────────────────────┘
```

**Два направления:**
1. **Файл → индекс.** `watchdog` следит за `vault/`; при изменении/создании `.md` парсер извлекает frontmatter + тело, обновляет строки в SQLite. Конфликты (одновременная правка) — индекс всегда можно пересобрать.
2. **UI → файл.** Правка заявки в веб/TMA → FastAPI сериализует изменения в frontmatter `.md` и пишет в файл → file watcher ловит изменение → обновляет индекс. Таким образом, индекс и файлы всегда синхронны, а Syncthing разносит `.md` на устройства.

**Защита от echo-loop (двойного сохранения):**
Направление (2) создаёт риск: бэкенд сам пишет `.md` → watcher мгновенно ловит то же изменение → переиндексация/гонка. Защита — **двухслойная**:
- **Own-write tracking (основная):** при записи `.md` бэкенд помечает путь в in-memory множестве «недавно записано мной»; watcher игнорирует следующее событие по этому пути (с коротким TTL, ~1–2 c).
- **`etag`-проверка (страховка):** переиндексация сравнивает хэш/`etag` файла со значением в `tasks.etag` (DATA_MODEL §3.1) и пропускается при совпадении. Защищает также от внешних Syncthing-событий без реального изменения контента.

**Полная пересборка индекса:** при старте или детекте рассинхрона — полный обход `vault/` + `config.yml`, пересоздание SQLite (таблицы + FTS5) и пересчёт векторов (`rag: true`-страниц через Gemini API). Это «сброс» к консистентному состоянию.

## 5. Авторизация и потоки

| Клиент | Механизм | Что получает |
|--------|----------|--------------|
| Веб (браузер) | **Telegram Login Widget** → валидация HMAC на бэке → JWT | JWT в cookie/localStorage; роль из контакта (`system_role`) |
| TMA (Telegram Mini App) | `Telegram.WebApp.initData` → HMAC-валидация → JWT | Тот же JWT; тот же API |
| ИИ-агенты / интеграции | **API Key** (`X-API-Key`) | Доступ к MCP/REST без Telegram |

**Сопоставление аккаунта:** Telegram-username → контакт с `team_member: true` и совпадающим `telegram` (VISION §3.8). Роль (`admin`/`member`) берётся из `system_role` этого контакта. Внешние исполнители (`team_member: false`) войти не могут.

## 6. Конфигурация и секреты

- **`config.yml`** (в vault, `.taskboard/`): схема — статусы, приоритеты, определения custom-полей. См. `VAULT_EXAMPLES.md`.
- **Переменные окружения** (`.env`, не в vault): `TELEGRAM_BOT_TOKEN`, `JWT_SECRET`, `GEMINI_API_KEY` (embedding + транскрипция), `API_KEYS_*`, пути к vault, и т.д.
- **Секреты НЕ хранятся в vault** (vault синхронизируется и редактируем — токены туда нельзя).

### 6.1 Разделение контента wiki (для RAG / Gemini)

Так как embedding считается через **Gemini API** (внешний сервис), критично не отправлять туда чувствительные данные. Применяется паттерн **whitelist + exclusion**:

- **Whitelist для RAG** (основной механизм): страница индексируется в векторную БД **только если** явно помечена `rag: true` в frontmatter. По умолчанию новые страницы **не эмбеддятся** — так случайный файл с секретом не уйдёт в Gemini.
- **Папка-исключение** `wiki/_secret/` — содержимое **никогда** не эмбеддится и не покидает vault (остаётся доступно в Obsidian и в локальном FTS5-поиске).
- **Секреты — в `.env`/secrets**, не в wiki. В wiki — плейсхолдеры (`см. .env`, `переменная PROD_ALPHA_SSH`), а регламент (без секрета) свободно индексируется.
- **Аудит**: в настройках/дашборде Admin видит список страниц, уходящих в Gemini (позволяет ревью перед включением RAG).

Примеры:
```yaml
---
rag: true        # явно разрешить embedding в Gemini
---
```
```yaml
---
sensitive: true  # НЕ отправлять в embedding (альтернатива/дополнение к _secret/)
---
```

> Локальный полнотекстовый поиск (FTS5) покрывает **весь** wiki, включая `_secret/` и `sensitive` — приватный поиск не уходит наружу. В Gemini уходят только векторы `rag: true`-страниц.

### 6.2 Первичная инициализация (Bootstrap — «курица и яйцо»)

На чистом VPS есть проблема: единственный способ входа — Telegram Login, но:
1. бот ещё не привязан к домену через `@BotFather`;
2. в `wiki/contacts/` ещё нет контакта первого Admin.

**Bootstrap = CLI + операционный шаг:**

**CLI-команда инициализации** (запускается на VPS один раз):
```bash
python -m app.cli init-admin --telegram "@murad" --name "Мурад"
# → создаёт дерево vault (tasks/, archive/, wiki/..., .taskboard/config.yml),
#   контакт-админ (team_member: true, system_role: admin), дефолтные статусы/приоритеты
```
Другие CLI-команды (§11):
- `init-vault` — только дерево папок + дефолтный `config.yml` (без админа).
- `reindex-all` — принудительная полная переиндексация из консоли.

**Операционный шаг (не код) — чеклист деплоя:**
1. Зарегистрировать бота в `@BotFather`, получить `TELEGRAM_BOT_TOKEN`.
2. **Привязать домен** к боту: `@BotFather → /setdomain → ваш-домен` (без этого Telegram Login Widget не заработает).
3. `docker compose up -d`.
4. `docker compose exec backend python -m app.cli init-admin ...` (первый Admin).
5. Дальше — вход через Telegram Login, создание остальных контактов через UI.

**DEV_AUTH_TOKEN для локальной разработки** (`.env`): при `DEV_AUTH_TOKEN=...` бэкенд выдаёт JWT по этому статическому токену (через `POST /auth/dev-token`) — позволяет отлаживать фронтенд/бекенд без Telegram Login Widget и без привязки домена. Работает **только** вне production (флаг `APP_ENV=production` отключает).

### 6.3 CORS / CSP для Telegram Mini App (TMA)

Telegram Mini App открывается внутри WebView/iframe мессенджера Telegram. Без правильных заголовков фронт не отрендерится. Требуется настроить в **Caddy** (и продублировать в FastAPI для API-ответов):

- `Content-Security-Policy: frame-ancestors https://web.telegram.org;` (разрешает встраивание TMA).
- `X-Frame-Options` **не выставляется**: `ALLOW-FROM` не поддерживается современными браузерами (заголовок игнорируется), а `DENY`/`SAMEORIGIN` сломали бы TMA. Достаточно CSP `frame-ancestors`.
- `Access-Control-Allow-Origin` — согласно источникам фронтенда (домен веб-версии + TMA).

Эти заголовки — часть `Caddyfile` и middleware FastAPI; без них TMA показывает пустой экран.

## 7. Развёртывание (Docker Compose)

Сервисы (пример состава `docker-compose.yml`):
- **`proxy`** — Caddy (TLS, реверс-прокси).
- **`frontend`** — Next.js (Node.js-контейнер).
- **`backend`** — FastAPI + aiogram-бот в **одном Python-контейнере** (решение по Q-A1, §10): uvicorn поднимает FastAPI, при старте spawn'ится бот-таска (один event loop).
- **`syncthing`** — синхронизация vault (или внешний уже стоящий, см. VISION §9).

**Volumes:**
- `vault/` — монтируется в `backend` (и в `syncthing`).
- `db/` — SQLite-индекс (включая FTS5 и векторы sqlite-vec).

**Health checks:** эндпоинты `/healthz` и `/ready` (проверка vault доступен, SQLite открывается, бот API отвечает) в FastAPI; интеграция с Docker HEALTHCHECK.

## 8. Нефункциональные свойства

- **Производительность:** канбан/список/поиск читают SQLite-индекс (мс); ленивый рендеринг доски (VISION §9.1).
- **Надёжность:** файлы = источник правды; при сбое индекса — пересборка. Syncthing-конфликты разрешаются на уровне файлов (минимальные диффы).
- **Безопасность:** HTTPS/TLS обязательно; JWT с коротким TTL + refresh; API Keys для ИИ-агентов; секреты в `.env`; **CORS/CSP для TMA** (§6.3).
- **Наблюдаемость** 🧩: структурированные логи (structlog), базовые метрики `/metrics` (Prometheus-формат) — опционально.
- **Резервное копирование:** vault синхронизирован на локальные машины (де-факто бэкап); SQLite-индекс (с векторами) регулярным dump-том Docker volume или пересобирается из vault.

## 9. CLI администратора (`app/cli.py`)

CLI-команды для операций, которые неудобно или невозможно делать через UI/API (bootstrap, обслуживание). Запускаются на VPS через `docker compose exec backend python -m app.cli ...`.

| Команда | Описание |
|---------|----------|
| `init-vault` | Первичная инициализация дерева vault (`tasks/`, `archive/`, `wiki/...`, `attachments/`) + дефолтный `config.yml`. |
| `init-admin --telegram @username --name "Имя"` | Создать контакт первого Admin (§6.2). Обычно запускается один раз после `init-vault`. |
| `reindex-all` | Принудительная полная переиндексация из консоли (обход vault + Gemini embedding). |
| `cleanup-orphans --older-than 7d` | Поиск/удаление осиротевших вложений (VISION §4.8) с age-фильтром. |

CLI — часть bootstrap-флоу (§6.2) и эксплуатационный инструмент. Не доступен через REST API.

## 10. Принятые архитектурные решения

### ✅ Q-A1. Бот и бэкенд — один контейнер
**Решение:** FastAPI и aiogram-бот в **одном Python-контейнере**; бот запускается как asyncio-таска в общем event loop с uvicorn. Шина событий — **in-memory `asyncio.Queue`** (без Redis/NATS).

**Обоснование (для контекста: малая команда, SQLite-файл, один VPS, принцип «компактность»):**
- **Доступ к SQLite из одного процесса** — тривиален (один писатель). Два контейнера потребовали бы WAL + `busy_timeout` и несли риск `database is locked` при конкурентных записях.
- **In-memory шина событий «бесплатна»** — не нужен внешний Redis/SQLite-outbox/HTTP-вебхук между сервисами (каждый из которых — лишняя точка отказа и сложности).
- **Меньше ресурсов и проще деплой** на одном VPS (один образ, один `docker compose up`, синхронные обновления без расхождения версий).
- Webhook бота ложится на тот же Caddy/FastAPI без отдельного маршрута.

**Принятые риски и страховки:**
- *Связанный жизненный цикл* (рестарт API = рестарт бота, общая точка отказа) — **приемлемо** для команды 2–3 чел.; перекрывается простотой.
- *Блокировка event loop* долгой работой может «подвесить» бот-таску → **страховка: вся долгая/сетевая работа выносится в background tasks / отдельные воркеры** (переиндексация vault, вызовы Gemini API для embedding/транскрипции, генерация PDF, рассылка уведомлений).
- *Сильная связанность кода* → **страховка: модульное разделение** (`app/api/`, `app/bot/`, `app/domain/`, `app/events/`, `app/indexer/`), чтобы при росте выделить бота в отдельный контейнер было недорогой операцией.

**Когда пересмотреть (миграция на 2 контейнера):** если аудио/RAG-нагрузка станет тяжёлой; при высоком потоке событий; при необходимости независимо скалировать/обновлять бота.

### ✅ Q-A2. Векторное хранилище + embedding
**Решение:**
- **Хранилище векторов — `sqlite-vec`** (расширение SQLite): векторы живут таблицей в едином `index.sqlite`. Один движок хранения, один файл для бэкапа, ноль лишних сервисов.
- **Embedding — Gemini API `text-embedding-004`** (768-dim, мультиязычная): лёгкий контейнер (без ML-веса), высокое качество на русском, free tier (1500 req/день) покрывает объём.
- **Разделение контента wiki** (§6.1): embedding в Gemini уходит **только** от страниц с `rag: true` (whitelist); `_secret/` и `sensitive` не покидают vault.

**Обоснование:**
- **sqlite-vec вместо ChromaDB** идеально ложится в архитектуру «файлы + единый SQLite-индекс» (Q-A1, DATA_MODEL §5): нет второй подсистемы хранения (DuckDB/Parquet), бэкап — один файл, меньше зависимостей. Для ~тысяч векторов brute-force поиск — миллисекунды; HNSW не нужен.
- **Embedding через API (Gemini)** оставляет контейнер FastAPI лёгким (нет PyTorch/ONNX-рантайма), что консистентно с Q-A1 (один компактный контейнер). Локальная MiniLM рассматривалась ради приватности, но паттерн разделения контента (§6.1) решает приватность дешевле — без ML-веса в контейнере.
- Мультиязычность Gemini критична для русскоязычного wiki.

**Принятые риски и страховки:**
- *Приватность (текст уходит в Google)* → **страховка: whitelist `rag: true` + папка `_secret/` + секреты в `.env`** (§6.1). Локальный FTS5-поиск покрывает весь wiki приватно; в Gemini уходят только явным образом разрешённые страницы.
- *Внешняя зависимость от Gemini API* (недоступность → RAG не работает) → RAG — фича «будущее» (🔥 в VISION), некритична для базового MVP; при недоступности Gemini семантический поиск просто временно недоступен, остальной функционал работает.
- *Free tier лимит (1500 req/день)* → при полной переиндексации wiki (~тысячи чанков) можно упереться; страховка: батчинг embedding-запросов (Gemini поддерживает батч) + построчная очередь индексации.
- *sqlite-vec моложе ChromaDB* → но стабилен и активно развивается; в крайнем случае миграция на ChromaDB in-process недорога.

**Когда пересмотреть:** при росте корпуса wiki до десятков тысяч документов (тогда HNSW в специализированной БД может стать оправданным); при ужесточении требований приватности (тогда переход на локальную embedding-модель).

### ✅ Q-A3. Транскрипция голоса
**Решение:** **Gemini API** (мультимодальная транскрипция через Gemini Flash/Pro) — вместо Whisper self-hosted.

**Обоснование:**
- **Единый провайдер с embedding** (Q-A2): один `GEMINI_API_KEY`, один SDK, один биллинг — простота интеграции и конфигурации.
- **Лёгкий контейнер** — нет тяжёлого ML-рантайма (Whisper large-v3 весит гигабайты и требует GPU для приемлемой скорости). Консистентно с решениями Q-A1/Q-A2 (один компактный контейнер без ML-веса).
- **Качество транскрипции русского** у Gemini на уровне Whisper, иногда лучше на разговорной речи с акцентами.
- Free tier Gemini покрывает поток голосовых от 2–3 человек.

**Принятые риски и страховки:**
- *Приватность (аудиосообщения уходят в Google)* — голосовые создаются самими членами команды для заявок, это не чувствительные данные клиентов; риск приемлем. Если кто-то диктует секрет — лучше не делать этого в голосовом (как и не писать секреты в plaintext-заявки).
- *Внешняя зависимость* (недоступность Gemini → голос не транскрибируется) → fallback: бот отвечает «не удалось распознать, создайте заявку текстом»; текстовый `/task` работает всегда.
- *Аудио отправляется как файл* → транскрипция в background task (не блокирует event loop, см. Q-A1 страховку).

**Когда пересмотреть:** при очень частых голосовых (тогда стоимость API может стать заметной — self-hosted Whisper дешевле в перспективе); при требованиях офлайн/приватности.

### ✅ Q-A4. Webhook vs polling для Telegram-бота
**Решение:** **Гибрид** — webhook в продакшене (VPS), polling при локальной разработке. Переключается флагом окружения `BOT_MODE=webhook|polling`. Код бота (aiogram `Dispatcher`) не зависит от способа получения апдейтов — разница только в источнике: webhook-роут FastAPI скармливает `Update` диспетчеру, либо фоновая polling-таска делает то же самое.

**Обоснование:**
- **В проде главное препятствие для webhook уже устранено** — FastAPI за Caddy с публичным доменом и TLS (решения по Q-A1/Q-A2). Добавить webhook = просто ещё один роут `/bot/webhook`, проксируемый Caddy. Мгновенная доставка, никакого оверхеда.
- **Polling незаменим в локальной разработке** (ноутбук за NAT, без публичного домена) — работает без туннелей (ngrok/cloudflare-tunnel).
- Единая кодовая база бота; переключение режимов — конфигурация, не код.

**Реализация (набросок, aiogram 3 canonical):**
```python
from aiogram.webhook.aiohttp_server import SimpleRequestHandler
# или для FastAPI — приём Update и передача в Dispatcher через bot-контекст

# webhook: используем aiogram SimpleRequestHandler-подход (корректный контекст бота)
@app.post("/bot/webhook")
async def bot_webhook(update: Update, _bot: Bot = Depends(get_bot)):
    async with _bot.context():
        await dispatcher.feed_update(_bot, update)
    return {"ok": True}

# запуск polling как asyncio-таски при старте (если BOT_MODE=polling)
@app.on_event("startup")
async def start_polling():
    if settings.BOT_MODE == "polling":
        asyncio.create_task(dispatcher.start_polling(bot))
```
В aiogram 3.x вызов `feed_update` требует корректного контекста бота — либо через `bot.context()`, либо через официальный webhook-адаптер `aiogram.webhook.*` (рекомендуемый путь для prod). В режиме polling тот же `Dispatcher` работает без webhook-роута.

**Принятые риски и страховки:**
- *Повторные доставки/дедупликация (webhook)* → aiogram сам дедуплицирует по `update_id`; отвечать 200 OK быстро, тяжёлую обработку — в background.
- *Бот упал, обновления копятся (webhook)* → при рестарте обработать накопленное; Telegram хранит ~24ч.
- *Один poller на токен (polling)* → для локального dev это не ограничение.

### ✅ Q-A5. Background-воркеры
**Решение:** **Гибрид** — `BackgroundTasks` FastAPI для I/O-bound + `run_in_executor` (thread pool) для CPU-bound (PDF). Всё в одном контейнере, без Redis/Celery.

**Обоснование:**
- **Почти вся background-нагрузка проекта — I/O-bound:** вызовы Gemini API (embedding, транскрипция), рассылка в Telegram, чтение/запись `.md`, парсинг frontmatter, переиндексация vault. Для таких задач `BackgroundTasks` (event loop) подходит идеально — не блокирует HTTP-запрос, выполняется после ответа.
- **CPU-bound только генерация PDF-отчётов** (через LaTeX/wkhtmltopdf). Это редкая задача (отчёты за период), не горячий путь. Через `run_in_executor` с thread pool — не блокирует event loop, остаётся в одном процессе.
- **Ноль внешних зависимостей** — ни Redis, ни Celery, ни Dramatiq, ни второго процесса. Полностью консистентно с Q-A1 (один компактный контейнер).
- **Единый писатель SQLite** — нет проблем с concurrent write (которые возникли бы с отдельным worker-контейнером).

**Принятые риски и страховки:**
- *CPU-bound задача может всё же заблокировать loop, если её забыть вынести в executor* → **страховка: конвенция кода** — любые CPU-операции (PDF, синтаксический разбор больших объёмов) выполняются **только** через `run_in_executor`; в `app/workers/` единое место для такой логики.
- *Потеря задачи при падении процесса* (в отличие от надёжной очереди Celery) → для ваших задач это приемлемо: индексация/уведомление перепоставится при следующем событии (file watcher снова сработает); критичные задачи можно дублировать в таблицу-аутбокс `outbox_jobs` (опц.).
- *GIL при thread pool для CPU-bound* → для PDF это не проблема (генерация освобождает GIL в C-коде wkhtmltopdf); при чисто-Python CPU-нагрузке — process pool.

**Когда пересмотреть (миграция на worker-контейнер):** при тяжёлой регулярной переиндексации (тысячи файлов); при частой PDF-генерации в пиковые часы; при необходимости фоновых задач с надёжными очередями/ретраями.
