# Структура vault и примеры Frontmatter

> Приложение к документу-видению (`VISION.md`). Конкретные шаблоны и примеры — как именно устроено хранение данных в Obsidian-vault. Эскиз, не финальная спецификация.

---

## 1. Структура vault

```
taskboard-vault/
├── tasks/                          # активные заявки + Done
│   ├── TB-0001-исправить-баг-авторизации.md
│   ├── TB-0002-добавить-экспорт-в-pdf.md
│   └── TB-0003-настройка-цветов-статусов.md
│
├── archive/                        # архивные .md-заявки (вложений тут НЕТ)
│   ├── TB-0000-старая-заявка.md
│   └── ...
│
├── attachments/                    # общая папка медиа (фото, PDF, DOCX…) — НЕ переносится при архивации
│   ├── screenshot-login-error.png
│   ├── spec-auth-module.pdf
│   └── report-2026-07.xlsx
│
├── wiki/                           # база знаний и справочники
│   ├── README.md
│   ├── projects/                   # ПРОЕКТЫ — wiki-страницы (метаданные во Frontmatter)
│   │   ├── project-alpha.md
│   │   └── project-beta.md
│   ├── clients/                    # КЛИЕНТЫ — wiki-страницы
│   │   ├── acme-corp.md
│   │   └── globex.md
│   ├── contacts/                   # КОНТАКТЫ (внешние исполнители) — wiki-страницы
│   │   ├── sysadmin.md
│   │   └── designer-anna.md
│   ├── regulations/                # регламенты и процессы
│   │   ├── process-onboarding.md
│   │   └── backup-policy.md
│   └── knowledge/                  # общая база знаний
│       ├── fastapi-tips.md
│       └── deployment-checklist.md
│
├── .taskboard/                     # системная папка (скрытая)
│   └── config.yml                  # ТОЛЬКО схема: статусы, приоритеты, определения custom-полей
│
└── .obsidian/                      # конфигурация Obsidian (стандартная)
```

**Ключевые принципы структуры:**
- **`tasks/` и `archive/`** — две зоны для заявок. Перенос между ними = смена статуса на «архивный» (§4.2, §9.1 в VISION.md).
- **`attachments/` — общая для всего vault.** Один и тот же файл может использоваться в нескольких заявках и wiki-страницах. При архивации заявки вложения **остаются на месте** (§4.8).
- **`wiki/`** — база знаний и **справочники**. Подпапки `projects/`, `clients/`, `contacts/` — это не просто заметки, а **хранилища справочных сущностей**: каждая сущность (проект/клиент/контакт) — wiki-страница с метаданными во Frontmatter (§9.2 в VISION.md). Подпапки `regulations/`, `knowledge/` — обычная база знаний.
- **`.taskboard/config.yml`** — хранит **только схему** (статусы, приоритеты, определения custom-полей). Проекты/клиенты/контакты здесь **не дублируются** — они живут в `wiki/`.
- **SQLite-индекс** (`index.sqlite`) — производный индекс по всем источникам; пересобирается из `.md`. Лежит **вне vault** (том `db/`, ARCHITECTURE §7), чтобы Syncthing его не синхронизировал.
- **Имя файла заявки** — человекочитаемое: `<ID>-<slug>.md` (например `TB-0001-исправить-баг-авторизации.md`). `slug` — краткий текст из заголовка для удобства в Obsidian; ID внутри файла — источник правды.

## 2. Frontmatter заявки

Заявка = wiki-страница с YAML Frontmatter (структурированные атрибуты) + Markdown-тело (описание, отчёты, логи времени, обсуждение).

### 2.1 Пример заявки

Файл: `tasks/TB-0001-исправить-баг-авторизации.md`

```markdown
---

id: TB-0001
title: "Исправить баг авторизации при входе через Telegram"

# === Классификация ===
project: project-alpha
client: acme-corp
status: In Progress
priority: High
tags: [bug, auth, telegram]

# === Исполнение ===
assignee: murad
author: murad
created: 2026-08-01T09:15:00+03:00
updated: 2026-08-08T14:30:00+03:00
due: 2026-08-10          # дедлайн вручную (дата или дата-время)
closed:                  # заполняется при переходе в Done/Archive

# === Пользовательские атрибуты (custom fields) ===
custom:
  client_ticket_number: "ACME-2026-0417"   # № заявки в системе заказчика
  client_ticket_date: 2026-07-30           # дата заявки заказчика — для финотчётов/сверки

# === Связи (wiki-ссылки на заявки/страницы) ===

  - "[[TB-0002]]"                           # связанная заявка
  - "[[projects/project-alpha]]"            # страница проекта
  - "[[regulations/auth-process]]"          # регламент
```

**Важно:** `assignee: sysadmin` ссылается на контакт с `team_member: false` — это **внешний исполнитель**. Система показывает его как исполнителя в канбане/списке/отчётах по нагрузке, но:
- он не имеет аккаунта и не входит в систему;
- личные уведомления ему **не уходят** — событие по заявке идёт только в общий командный чат;
- команда передаёт задачу ему внешним путём и фиксирует ход в описании/комментариях.

> `assignee` **всегда** равен `key` контакта (и для члена команды, и для внешнего исполнителя). Если `sysadmin` станет членом команды, `assignee` в этой заявке менять не нужно — история сохранится (см. §3.2).

### 2.3 Поля Frontmatter — справочник

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `id` | строка | да | Простой сквозной номер (`TB-0001`). Источник правды для идентификации. |
| `title` | строка | да | Заголовок заявки. |
| `project` | строка | нет | Имя/ключ проекта (`project-alpha`). Ссылается на `wiki/projects/`. |
| `client` | строка | нет | Имя/ключ клиента (`acme-corp`). Ссылается на `wiki/clients/`. |
| `status` | строка | да | Статус заявки — имя статуса из `config.yml` (`Backlog`, `To Do`, `In Progress`, `Review/Testing`, `Done`, `On Hold`, `Archived`). |
| `priority` | строка | нет | Приоритет — имя из `config.yml` (`Critical`, `High`, `Medium`, `Low`). |
| `tags` | список строк | нет | Теги для фильтрации и группировки. |
| `assignee` | строка | нет | Исполнитель (всегда один) — `key` контакта из `wiki/contacts/` (напр. `murad` для члена команды, `sysadmin` для внешнего исполнителя). Внешний контакт не имеет доступа к системе и не получает уведомлений (§2, §3.8). |
| `author` | строка | да | Автор заявки. |
| `created` | дата-время | да | Дата/время создания (ISO 8601 с таймзоной). |
| `updated` | дата-время | да | Дата/время последнего изменения (обновляется автоматически). |
| `due` | дата/дата-время | нет | Дедлайн, задаётся **вручную**. |
| `closed` | дата-время | нет | Дата закрытия (переход в `done`/`archived`). Пусто, пока открыта. |
| `custom` | объект | нет | Пользовательские атрибуты (см. §4.5). Структура задаётся в `.taskboard/config.yml`. |
| `links` | список wiki-ссылок | нет | Связи с другими заявками и wiki-страницами. |

**Примечания:**
- `assignee` — всегда один или пусто (не назначен). Смена исполнителя = изменение этого поля + запись в историю (см. §3.1).
- `custom` — словарь «ключ: значение»; набор ключей и их типы настраиваются через `.taskboard/config.yml`. Это позволяет добавлять/удалять поля без изменения структуры заявок.
- `links` дублируют wiki-ссылки в теле документа: заявку можно ссылать и прямо из Markdown `[[TB-0002]]`, и явно в `links` для индексации связей.

## 3. Где что хранится: схема (config.yml) и справочники (wiki-страницы)

Принцип: **файлы — источник правды, SQLite — индекс** (§9.2 в VISION.md).

- **`config.yml`** хранит только **схему** (стабильную структуру): статусы, приоритеты, определения custom-полей. Этот файл **не растёт** от числа проектов/клиентов/контактов.
- **Проекты, клиенты, контакты** — это **wiki-страницы** в `wiki/projects/`, `wiki/clients/`, `wiki/contacts/` с метаданными во Frontmatter. Они редактируются независимо (каждая правка = свой файл → нет конфликтов синхронизации) и дают **backlinks** на связанные заявки.

### 3.1 Пример `.taskboard/config.yml` (только схема)

```yaml
# Статусы заявок (гибкие — добавляются/удаляются через UI)
statuses:
  - name: Backlog
    type: initial          # категория: initial | progress | final | on_hold | archive
    color: "#9e9e9e"       # цвет рамки/бейджа статуса
    on_board: true         # показывать на канбане
    order: 1
  - name: To Do
    type: initial
    color: "#2196f3"
    on_board: true
    order: 2
  - name: In Progress
    type: progress
    color: "#ff9800"
    on_board: true
    order: 3
  - name: Review/Testing
    type: progress
    color: "#9c27b0"
    on_board: true
    order: 4
  - name: Done
    type: final
    color: "#4caf50"
    on_board: true         # Done ВИДЕН на доске
    system: true           # системный — защищён от удаления
    order: 5
  - name: On Hold
    type: on_hold
    color: "#607d8b"
    on_board: true
    order: 6
  - name: Archived
    type: archive
    color: "#bdbdbd"
    on_board: false        # архив НЕ показывается на доске
    system: true
    order: 7

priorities:
  - { name: Critical, color: "#f44336", order: 1 }
  - { name: High,     color: "#ff9800", order: 2 }
  - { name: Medium,   color: "#2196f3", order: 3 }
  - { name: Low,      color: "#9e9e9e", order: 4 }

# Пользовательские атрибуты заявок (custom fields)
custom_fields:
  - key: client_ticket_number
    label: "Номер заявки заказчика"
    type: text
    required: false
  - key: client_ticket_date
    label: "Дата заявки заказчика"
    type: date
    required: false

# Проекты, клиенты, контакты ЗДЕСЬ НЕ ХРАНЯТСЯ — они wiki-страницы (см. §3.2).
```

### 3.2 Примеры справочных сущностей как wiki-страниц

**Проект** — файл `wiki/projects/project-alpha.md`:

```markdown
---
type: project
key: project-alpha
name: "Project Alpha"
client: acme-corp          # ссылка на wiki/clients/acme-corp.md
color: "#e91e63"
tags: [web, fastapi]
---

# Project Alpha

Проект сопровождения веб-приложения для Acme Corp.

## Технологии
- Backend: FastAPI
- Frontend: Next.js
- БД: PostgreSQL

## Полезные ссылки
- [[regulations/auth-process]] — регламент процесса авторизации
- [[TB-0001]] — текущий баг по авторизации
```

**Клиент** — файл `wiki/clients/acme-corp.md`:

```markdown
---
type: client
key: acme-corp
name: "Acme Corp"
---

# Acme Corp

Заказчик проекта Alpha. Контакты и реквизиты…
```

**Контакт — член команды** (`team_member: true`) — файл `wiki/contacts/murad.md`:

```markdown
---
type: contact
key: murad
name: "Мурад"
role: "Разработчик"
team_member: true
telegram: "@murad"           # для входа (Telegram Login) и уведомлений
system_role: admin           # admin | member
email: "murad@example.com"
---

# Мурад

Ведущий разработчик, Admin системы.
```

**Контакт — внешний исполнитель** (`team_member: false`) — файл `wiki/contacts/sysadmin.md`:

```markdown
---
type: contact
key: sysadmin
name: "Иван Сисадмин"
role: "Системный администратор"
team_member: false           # без аккаунта, без входа и уведомлений
organization: "HostingPro"
email: "ivan@hostingpro.example"
phone: "+7-900-000-00-00"
---

# Иван Сисадмин

Обслуживает сервера наших проектов. Связь — по телефону/email.
```

Заявка ссылается на любой контакт одинаково — по `key` в поле `assignee`: `assignee: murad` или `assignee: sysadmin`. Obsidian покажет обратную ссылку на странице контакта (все назначенные на него заявки).

**Переход между ролями** (ключевая возможность модели «единая личность»):
- Если сисадмин `sysadmin` становится членом команды — у того же контакта (`key: sysadmin`) добавляем `team_member: true`, `telegram`, `system_role`. Он получает вход и уведомления, **а все прежние заявки и логи времени остаются за `sysadmin`**.
- Если член команды уходит во внешние — убираем эти поля; человек остаётся в системе как внешний исполнитель, история сохраняется.
- Поле `assignee` в заявках при этом **не меняется** — вот почему история не рвётся.

### 3.3 Что важно в этой модели
- **`config.yml` — только схема**: статусы, приоритеты, определения custom-полей. Не растёт со временем (~80–100 строк).
- **Справочники — wiki-страницы**: метаданные проектов/клиентов/контактов в Frontmatter, описание в теле. Нет дублирования между wiki и конфигом.
- **Нет конфликтов синхронизации**: правка одного контакта = правка одного файла, а не общего `config.yml`.
- **Backlinks**: страница проекта/контакта автоматически показывает связанные заявки (и в Obsidian, и в нашем UI).
- **Контакт = единая личность исполнителя**: `assignee` всегда равен `key` контакта. Член команды и внешний исполнитель — один тип сущности, различаются `team_member`. При смене роли `key` не меняется → история заявок сохраняется (VISION §2.3).
- **Цвета** (`color`) и **видимость на доске** (`on_board`) статусов хранятся в `config.yml` → канбан и список сразу их подхватывают.
- **Тип статуса** (`type`) управляет жизненным циклом; архивный тип скрывает статус с доски. Системные статусы (`system: true`) защищены от удаления.
- **Custom-поля** — определения в `config.yml`; значения лежат в `custom:` Frontmatter каждой заявки.
- **SQLite** (`index.sqlite`) — производный индекс по `config.yml` + всем wiki-страницам + заявкам; пересобирается из файлов.

## 4. Wiki-страницы (база знаний и регламенты)

В `wiki/` живут не только справочники (§3.2), но и обычные страницы базы знаний и регламентов — обычные Markdown-файлы с Frontmatter (или без него). Они свободно связываются wiki-ссылками с заявками и справочниками.

Пример: `wiki/regulations/auth-process.md`

```markdown
---
type: regulation
title: "Регламент процесса авторизации"
tags: [auth, security]
---

# Регламент процесса авторизации

Описывает шаги входа через Telegram Login и обработку `auth_date`.

## Связанные заявки
- [[TB-0001]] — баг авторизации (устаревший auth_date)

## Связанные проекты
- [[projects/project-alpha]]
```

Связи работают в обе стороны: из заявки на wiki-страницу и обратно. **Обратные ссылки (backlinks)** видны и в Obsidian, и в нашем интерфейсе — так, на странице контакта «Иван Сисадмин» автоматически появятся все заявки, где он назначен исполнителем.

## 5. Резюме принципов хранения

1. **Заявка = wiki-страница** с YAML Frontmatter. Это даёт неограниченный Markdown-текст и wiki-ссылки.
2. **Frontmatter** хранит структурированные атрибуты; **тело** — описание, отчёты, логи времени, обсуждение.
3. **Две зоны**: `tasks/` (активные + Done) и `archive/` (архив).
4. **`attachments/` — общая папка**, не переносится при архивации.
5. **Файлы — источник правды, SQLite — индекс** (производный, пересобирается из `.md`).
6. **Схема** (статусы, приоритеты, определения custom-полей) — в `.taskboard/config.yml`; не растёт со временем.
7. **Справочники** (проекты, клиенты, контакты) — **wiki-страницы** с метаданными во Frontmatter; дают backlinks и не конфликтуют при синхронизации.
8. **Переносимость**: всё хранится в Markdown + YAML; vault можно открыть в Obsidian, забрать с собой, или пересобрать индекс из файлов.
