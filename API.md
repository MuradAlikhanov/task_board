# Task Board — API

> Приложение к `VISION.md`, `ARCHITECTURE.md`, `DATA_MODEL.md`. Уровень: список ресурсов и эндпоинтов с методами (без полных JSON-контрактов). Базовый путь: `/api/v1`.

---

## 1. Принципы

- **REST**, JSON. Версионирование в пути (`/api/v1`); breaking changes — только в новом мажоре (Q-P1, §16).
- **Авторизация:** Bearer JWT (веб/TMA) или `X-API-Key` (ИИ-агенты). Ключи — per-интеграция, полный доступ (Q-P4, §16). См. §3.
- **Идемпотентность:** мутации поддерживают заголовок `Idempotency-Key` (Q-P3, §16).
- **Чтения** идут в SQLite-индекс (быстро); **записи** сериализуются в `.md` и затем отражаются в индексе watcher'ом (VISION §9.2, ARCHITECTURE §4).
- **Пагинация:** `?page=&size=` (по умолчанию `size=50`). Сортировка: `?sort=field,asc|desc`. Фильтры — query-параметры.
- **Ошибки:** единый формат `{ "error": { "code", "message", "details" } }` со стандартными HTTP-кодами.
- **OpenAPI:** FastAPI автогенерирует схему на `/api/v1/openapi.json` и Swagger UI на `/docs` (только для Admin).

## 2. Аутентификация и сессии

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| POST | `/auth/telegram-login` | Веб-вход: приём данных Telegram Login Widget → HMAC-валидация → выдача JWT. Сопоставление username → контакт (`team_member: true`). |
| POST | `/auth/tma` | TMA-вход: приём `Telegram.WebApp.initData` → HMAC-валидация → JWT. |
| POST | `/auth/refresh` | Обновление JWT по refresh-токену. |
| GET | `/auth/me` | Текущий контакт (из JWT): профиль, роль, права. |
| POST | `/auth/dev-token` | **Только non-production** (`APP_ENV≠production`): обмен `DEV_AUTH_TOKEN` → JWT. Для локальной отладки без Telegram Login (ARCHITECTURE §6.2). В проде эндпоинт отключён. |

**API Keys** (для ИИ-агентов/интеграций) не имеют эндпоинта входа — передаются в заголовке `X-API-Key` при каждом запросе. Управляются через `/settings/api-keys` (§10). Ключи — **per-интеграция, полный доступ** (можно отозвать точечно); гранулярные права — будущее (Q-P4, §16).

## 3. Авторизация на эндпоинтах

- **Public:** `/auth/*`, `/healthz`, `/ready`.
- **Member** (любой член команды): чтение всего, создание/правка заявок/wiki, свои подписки.
- **Admin:** всё, что Member, + управление настройками (статусы, приоритеты, custom-поля, api-keys), проектами, клиентами, контактами, триггеры синхронизации/переиндексации.

## 4. Заявки (Tasks)

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| GET | `/tasks` | Список заявок с фильтрами/группировкой/сортировкой (ядро представления «Список», VISION §4.1.2). |
| POST | `/tasks` | Создание заявки (→ пишет `.md` в `tasks/`). Поддерживает `Idempotency-Key` (Q-P3, §16). |
| GET | `/tasks/{id}` | Карточка заявки (детальный просмотр, VISION §4.1.4). |
| PATCH | `/tasks/{id}` | Частичное обновление заявки (статус, assignee, приоритет, дедлайн и т.д.). Каждое изменение значимых полей → запись в историю. |
| DELETE | `/tasks/{id}` | Удаление заявки (удаляет `.md`). Требует подтверждения; для закрытых предпочтительнее архивация. |
| POST | `/tasks/{id}/archive` | Перевод в архив (файл `tasks/`→`archive/`, статус→архивный). VISION §4.2. |
| POST | `/tasks/{id}/unarchive` | Возврат из архива. |
| GET | `/tasks/{id}/history` | История изменений заявки (из `tasks_history`, DATA_MODEL §4.1). |
| POST | `/tasks/{id}/time-logs` | Добавить запись лога времени. |
| GET | `/tasks/{id}/time-logs` | Логи времени заявки. |

**Параметры `GET /tasks` (фильтры/группировка):**
- `project`, `client`, `status`, `assignee`, `priority`, `tag`, `due_before`, `due_after`, `overdue` (bool), `unassigned` (bool).
- `archived` (по умолчанию `include` — архив включён в поиск; `exclude` — без архива; `only` — только архив) — VISION Q-3.
- `q` — полнотекстовый поиск (FTS5, по умолчанию включает архив).
- `group_by` — атрибут группировки (project/client/status/assignee/priority/due/created/tag) — VISION §4.1.2.
- `view` — имя сохранённого представления (§9).

## 5. Канбан (доска)

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| GET | `/board` | Конфигурация доски: статусы (видимые на доске, `on_board=true`), их порядок/цвета, и карточки по колонкам. |
| GET | `/board?status=&limit=` | Лимитированная/пагинированная выборка по колонке (ленивый рендеринг, VISION §9.1). |
| PATCH | `/board/move` | Перенос карточки между колонками (смена статуса). Тело: `{task_id, to_status, position}`. |

Канбан — это специализированная проекция `/tasks` (фильтр `archived=exclude` + группировка по статусу + ленивая подгрузка). Отдельные эндпоинты — для удобства фронтенда.

| Метод | Эндпоинт | Описание |
|-------|----------|----------|
| GET | `/settings` | Текущая схема (`config.yml`): статусы, приоритеты, custom-поля. |
| PUT | `/settings/statuses` | CRUD статусов (с правилами безопасного удаления + миграции заявок). VISION §4.2. |

| GET/POST/PATCH/DELETE | `/settings/custom-fields` | Определения custom-полей. |

## 13. MCP / AI-агенты 🔥

Для ИИ-агентов API доступен по **API Key** (`X-API-Key`) и дополнительно как **MCP-сервер** (Model Context Protocol), предоставляющий инструменты (tools):

| Tool | Эквивалент REST | Описание |
|------|-----------------|----------|
| `search_tasks` | `GET /tasks?q=` | Полнотекстовый/фильтрованный поиск заявок. |
| `get_task` | `GET /tasks/{id}` | Читать заявку. |
| `create_task` | `POST /tasks` | Создать заявку (из голоса/текста бота). |
| `update_task_status` | `PATCH /tasks/{id}` | Сменить статус. |
| `search_wiki` | `GET /wiki/search` | Семантический/FTS поиск по wiki (RAG). |
| `assign_task` | `PATCH /tasks/{id}` | Назначить исполнителя (контакт). |

MCP-эндпоинт: `/mcp` (SSE или stdio-мост). Те же операции, что REST, но в формате tools для LLM-агентов. Авторизация — по API Key.

## 14. Telegram-бот (вебхуки/команды)

Не REST, но часть API-поверхности. Бот слушает webhook `/bot/webhook` (проксируется Caddy):

- Команды: `/task <текст>`, `/my`, `/status <id>`.
- Голос → Gemini (транскрипция) → `create_task`.
- Уведомления по событиям (от backend через внутреннюю шину событий).
- TMA открывает Next.js-фронтенд с тем же JWT-потоком (`/auth/tma`).

## 15. Примеры типовых сценариев (маппинг на API)

- **Создание заявки:** `POST /tasks` → FastAPI пишет `.md` → watcher индексирует → `GET /tasks/{id}` возвращает карточку.
- **Drag&drop в канбане:** `PATCH /board/move` (`task_id`, `to_status`) → меняет `status` в `.md` → watcher обновляет индекс → уходит событие уведомления.
- **Поиск по клиенту (отчёт):** `GET /tasks?client=acme-corp&due_after=...&due_before=...&group_by=project` → список для отчёта → `GET /reports/summary?...&format=pdf`.
- **Добавить ссылку на wiki:** `GET /wiki/search?q=auth` → выбор → `PATCH /tasks/{id}` добавляет `links`.
- **Смена статуса Done→Архив:** `POST /tasks/{id}/archive` → перенос файла + статус.
- **ИИ-агент ищет контекст:** MCP `search_wiki` + `search_tasks` (RAG) → ответ в Telegram.

## 16. Принятые решения по API

- ✅ **Q-P1. Версионирование API — URL-версионирование** (`/api/v1`, `/api/v2`, …). Breaking changes — только в новом мажоре; старая версия держится deprecated N месяцев. Non-breaking (новые поля/эндпоинты) — в рамках `/v1`. Для внутреннего продукта малой команды этого достаточно; ужесточается при появлении внешних потребителей.
- ✅ **Q-P2. Вебхуки наружу — отложено (🔥 будущее).** Сейчас события идут только внутренне (шина событий → бот). Фундамент заложен: добавить исходящий webhook-диспатчер поверх существующей `asyncio.Queue` (ARCHITECTURE Q-A1) позже — простая операция. В MVP не нужно.
- ✅ **Q-P3. Идемпотентность мутаций — заголовок `Idempotency-Key`.** На `POST /tasks` (и при необходимости на `PATCH`/`DELETE`) клиент передаёт UUID; сервер хранит результат запроса в таблице SQLite с TTL и при повторе с тем же ключом возвращает сохранённый результат вместо создания дубля (стандартный паттерн Stripe). Защищает от двойных кликов/ретраев, особенно при создании через бота/ИИ.
- ✅ **Q-P4. API-ключи — per-интеграция, полный доступ.** Отдельный ключ на каждую интеграцию (можно отозвать точечно, не затрагивая другие). Все ключи дают **полный доступ** (как у роли Member); гранулярные права (read-only, только-заявки и т.д.) — 🔥 будущее. Баланс безопасности и простоты для малой команды.
