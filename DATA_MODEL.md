# Task Board — Модели данных

> Приложение к `VISION.md` и `ARCHITECTURE.md`. Уровень: высокоуровневые модели данных. Принцип: **файлы — источник правды, SQLite — индекс** (VISION §9.2). Здесь описаны обе стороны: структура `.md`-файлов vault и схема SQLite-индекса.

---

## 1. Двойственность данных

| Слой | Что | Роль |
|------|-----|------|
| **Vault (`.md` + frontmatter)** | Человекочитаемые файлы, редактируемые в Obsidian | **Источник правды** (source of truth) |
| **SQLite-индекс** (`index.sqlite`) | Таблицы + FTS5 + **векторы (sqlite-vec)** | **Производный индекс** для быстрых запросов (канбан, списки, поиск, отчёты, RAG) |
| **`.taskboard/config.yml`** | Статусы, приоритеты, определения custom-полей | **Схема** (настройки) |
| **Gemini API** | Embedding-модель (внешняя) | Считает векторы для RAG; сами векторы хранятся в SQLite |

> Правило: при любом расхождении vault выигрывает; SQLite (включая векторы) пересобирается из файлов. Прямая правка SQLite в обход файлов запрещена.


---

## 2. Vault-сущности (источник правды)

Полные примеры frontmatter — в `VAULT_EXAMPLES.md`. Здесь — сводка атрибутов.

### 2.1 Заявка (`tasks/` или `archive/`)
`id`, `title`, `project` (→ wiki-страница), `client`, `status`, `priority`, `tags`, `assignee` (→ контакт `key`), `author`, `created`, `updated`, `due`, `closed`, `custom` (объект), `links` (wiki-ссылки). Тело: Markdown (описание, отчёты, логи времени).

### 2.2 Контакт (`wiki/contacts/`)
`key`, `name`, `role`, `team_member` (bool), `telegram`, `system_role` (admin/member), `email`, `phone`, `organization`. **Единая личность исполнителя** — `assignee` всегда = `key` контакта (VISION §3.8).

### 2.3 Проект (`wiki/projects/`)
`key`, `name`, `client`, `color`, `tags`, описание в теле.

### 2.4 Клиент (`wiki/clients/`)
`key`, `name`, описание в теле.

### 2.5 Wiki-страница (`wiki/...`)
Произвольный `.md` с опциональным frontmatter (`type`, `title`, `tags`).

### 2.6 Схема (`config.yml`)
Статусы (с `type`/`color`/`on_board`/`system`), приоритеты, определения custom-полей (`key`/`label`/`type`/`required`).

## 3. SQLite-индекс (производный)

Схема — денормализованный индекс для быстрых чтений. Не нормализован намеренно: цель — скорость выборок для канбана/списка/отчётов, а не OLTP. Все таблицы пересобираются из vault.

> Нотация ниже — псевдо-SQL/таблицы (имена колонок, типы, ключи), не финальный DDL.

### 3.1 `tasks` — заявки
| Колонка | Тип | Описание |
|---------|-----|----------|
| `id` | TEXT PK | `TB-0001` (из frontmatter `id`) |
| `file_path` | TEXT | путь к `.md` (`tasks/...` или `archive/...`) |
| `title` | TEXT | заголовок |
| `body_md` | TEXT | Markdown-тело (для поиска/предпросмотра) |
| `project_key` | TEXT FK→projects | ссылка на проект |
| `client_key` | TEXT FK→clients | ссылка на клиента |
| `status` | TEXT | статус (имя) |
| `status_type` | TEXT | категория статуса (initial/progress/final/on_hold/archive) |
| `priority` | TEXT | приоритет |
| `assignee_key` | TEXT FK→contacts | исполнитель (контакт) |
| `author_key` | TEXT FK→contacts | автор (контакт) |
| `due` | TIMESTAMP | дедлайн |
| `created` | TIMESTAMP | дата создания |
| `updated` | TIMESTAMP | дата обновления |
| `closed` | TIMESTAMP | дата закрытия |
| `is_archived` | INTEGER | 1 если `file_path` в `archive/` (денорм. для быстрого фильтра) |
| `etag` | TEXT | хэш/версия файла (для инкрементальной индексации) |

`status_type`, `is_archived` — денормализованные поля для быстрых фильтров канбана/списка (не хранятся в frontmatter, выводятся из `config.yml` + расположения файла).

### 3.2 `tasks_custom` — значения custom-полей (EAV)
| Колонка | Тип | Описание |
|---------|-----|----------|
| `task_id` | TEXT FK→tasks | заявка |
| `field_key` | TEXT | ключ поля (из `config.yml`) |
| `value_text` | TEXT | текстовое значение |
| `value_number` | REAL | числовое значение |
| `value_date` | TIMESTAMP | дата |

EAV-модель: позволяет добавлять/удалять custom-поля без миграций схемы. Тип значения определяется определением поля в `config.yml`.

### 3.3 `tasks_tags` — теги заявок (M:N)
| Колонка | Тип |
|---------|-----|
| `task_id` | TEXT FK→tasks |
| `tag` | TEXT |

### 3.4 `tasks_links` — связи заявок (M:N)
| Колонка | Тип | Описание |
|---------|-----|----------|
| `task_id` | TEXT FK→tasks | исходная заявка |
| `target_ref` | TEXT | **нормализованная** цель ссылки (см. ниже) |
| `target_type` | TEXT | тип цели (task/project/contact/wiki) — выводится из ссылки |

**Нормализация wikilinks (обязательно):** ссылки `[[...]]` из Obsidian могут отличаться регистром (`[[Projects/Project-Alpha]]` vs `[[projects/project-alpha]]`), слешами (Windows `\` vs Linux `/`) и расширением (`.md` или без). Поскольку vault синхронизируется между Windows/macOS (локальный Obsidian) и Linux (VPS), без нормализации **backlinks будут ломаться**. При индексации парсер приводит `target_ref` к каноническому виду: **lowercase, прямой слеш `/`, без расширения `.md`**. Поиск backlinks (`/links/backrefs`) идёт по нормализованному ключу.

### 3.5 `contacts` — контакты (члены команды + внешние)
| Колонка | Тип | Описание |
|---------|-----|----------|
| `key` | TEXT PK | ключ контакта (`murad`, `sysadmin`) |
| `file_path` | TEXT | `wiki/contacts/<key>.md` |
| `name` | TEXT | имя |
| `role` | TEXT | специализация |
| `team_member` | INTEGER | 0/1 |
| `telegram` | TEXT | username (для членов команды) |
| `system_role` | TEXT | admin/member (для членов команды) |
| `email` | TEXT | |
| `phone` | TEXT | |
| `organization` | TEXT | |

### 3.6 `projects` / `clients`
| Колонка | Тип | Описание |
|---------|-----|----------|
| `key` | TEXT PK | ключ |
| `file_path` | TEXT | wiki-страница |
| `name` | TEXT | название |
| `client_key` | TEXT | (только projects) ссылка на клиента |
| `color` | TEXT | (только projects) цвет |
| `body_md` | TEXT | текст страницы |

### 3.7 `wiki_pages` — прочие wiki-страницы (для поиска/backlinks)
| Колонка | Тип | Описание |
|---------|-----|----------|
| `path` | TEXT PK | путь в vault |
| `type` | TEXT | тип страницы (regulation/knowledge/...) |
| `title` | TEXT | заголовок |
| `body_md` | TEXT | текст |
| `rag` | INTEGER | 0/1 — индексировать ли в векторную БД (whitelist, ARCHITECTURE §6.1) |
| `sensitive` | INTEGER | 0/1 — помечена чувствительной (не эмбеддить) |
| `etag` | TEXT | хэш для инкрементальной индексации |

`rag`/`sensitive` выводятся из frontmatter страницы (см. §5.2). Страницы в `wiki/_secret/` неявно `rag=0`.

### 3.8 `attachments_index` — индекс вложений (для поиска осиротевших)
| Колонка | Тип | Описание |
|---------|-----|----------|
| `path` | TEXT PK | путь в `attachments/` |
| `referenced_by` | TEXT | страница/заявка, ссылающаяся на файл |
| `size` | INTEGER | размер |

Служит для утилиты очистки осиротевших вложений (VISION §4.8).

### 3.9 `config_snapshot` — снимок схемы (для целостности)
Таблица- KV, хранит разобранный `config.yml` (статусы, приоритеты, определения custom-полей). Используется для JOIN-ов (напр., получить `status_type`/`color`/`on_board` для статуса) без перечитывания YAML при каждом запросе.

### 3.10 Полнотекстовый поиск — FTS5
- **`tasks_fts`** (внешний контент → `tasks`): `title`, `body_md`, `tags`. Поиск заявок.
- **`wiki_fts`** (внешний контент → `wiki_pages` + `projects` + `clients`): `title`, `body_md`. Поиск wiki (VISION §4.7).
- По умолчанию поиск **включает архив**; фильтр по `is_archived=0` исключает архив (VISION Q-3).

### 3.11 `notifications_log` — журнал уведомлений (опц. 🧩)
| Колонка | Тип | Описание |
|---------|-----|----------|
| `id` | INTEGER PK | |
| `event` | TEXT | тип события |
| `task_id` | TEXT | связанная заявка |
| `channel` | TEXT | common_chat / personal |
| `recipient_key` | TEXT | контакт-получатель (для личных) |
| `sent_at` | TIMESTAMP | |

## 4. История изменений (audit trail)

История смены статуса и переназначения (VISION §3.1) хранится **в теле заявки** как Markdown-секция в конце файла (решение Q-D2, §8), и **дублируется в индекс** для быстрой выборки в дашборде. UI скрывает секцию истории при редактировании описания.

### 4.1 `tasks_history` (в индексе)
| Колонка | Тип | Описание |
|---------|-----|----------|
| `id` | INTEGER PK | |
| `task_id` | TEXT FK→tasks | |
| `at` | TIMESTAMP | момент |
| `actor_key` | TEXT FK→contacts | кто изменил |
| `field` | TEXT | что изменилось (status/assignee/...) |
| `old_value` | TEXT | |
| `new_value` | TEXT | |

> Источник правды для истории — тоже `.md`-файл (запись appended в тело), таблица в индексе — лишь отражение для быстрых запросов.

## 5. RAG-индекс (sqlite-vec, в index.sqlite)

Векторы хранятся в той же `index.sqlite` через расширение **sqlite-vec** (решение по Q-A2, ARCHITECTURE §9). Embedding считается через **Gemini API `text-embedding-004`** (768-dim).

### 5.1 `wiki_chunks` — векторная таблица
| Колонка | Тип | Описание |
|---------|-----|----------|
| `id` | INTEGER PK | |
| `source_path` | TEXT | путь к исходной wiki-странице |
| `chunk_index` | INTEGER | порядковый номер чанка в странице |
| `chunk_text` | TEXT | текст чанка |
| `embedding` | vec(768) | вектор (sqlite-vec) |
| `source_type` | TEXT | wiki/project/contact/task |
| `tags` | TEXT | теги (для метаданных) |

Поиск — SQL-функцией sqlite-vec (напр. `vec_distance_cosine(embedding, ?)` → ближайшие соседи).

### 5.2 Разделение контента (что эмбеддится)

В соответствии с паттерном разделения (ARCHITECTURE §6.1):
- В `wiki_chunks` попадают **только** страницы с `rag: true` в frontmatter (whitelist).
- Страницы из `wiki/_secret/` и с `sensitive: true` **исключены** из векторной индексации (но остаются в FTS5).
- Таким образом, в Gemini уходят только явным образом разрешённые страницы; чувствительные данные не покидают vault.

### 5.3 Когда пересчитывается
- При изменении wiki-страницы (watcher) → чанк пересоздаётся, embedding перевычисляется через Gemini API.
- Полная переиндексация — обход всех `rag: true`-страниц, батчинг запросов к Gemini API (лимит free tier 1500 req/день).

## 6. Жизненный цикл и инварианты

- **Создание заявки** → пишется новый `.md` в `tasks/` → watcher индексирует → новая строка в `tasks`.
- **Смена статуса** → правится `status` в frontmatter `.md` (файл остаётся в `tasks/`) → watcher обновляет `tasks.status`. Если новый статус типа `archive` → **файл переносится** `tasks/`→`archive/`, `is_archived=1` (VISION §9.1).
- **Смена исполнителя** → правится `assignee` в `.md` + запись в `tasks_history`. Внешний/член команды — без разницы, всегда `key` контакта.
- **Смена роли контакта** (член команды↔внешний) → правится `team_member`/`telegram`/`system_role` в `wiki/contacts/<key>.md` → `assignee` в заявках **не меняется** → история сохраняется (VISION §2.3).
- **Удаление custom-поля** → убирается из `config.yml` → при переиндексации строки `tasks_custom` для этого `field_key` игнорируются (значения в `.md` остаются, но не отображаются).

---

## 7. Производительность

- **Индексы SQLite:** на `status`, `assignee_key`, `project_key`, `due`, `is_archived`, `priority` (частые фильтры канбана/списка).
- **FTS5** покрывает полнотекстовый поиск без отдельного сервиса.
- **Ленивый рендеринг доски:** канбан запрашивает только N карточек на колонку (`LIMIT` + сортировка), не все заявки (VISION §9.1).
- **`etag`** на файлах → инкрементальная индексация (переиндексируем только изменившиеся файлы).

## 8. Принятые решения по данным

- ✅ **Q-D1. `body_md` целиком в индексе.** Превью/lazy-загрузка — преждевременная оптимизация: реальный объём (~1000 заявок × ~5 КБ = ~5 МБ, в крайнем случае ~50 МБ) для SQLite/FTS5 ничтожен. При отрисовке доски/списка API выбирает строки **без** `body_md` (только нужные поля), поэтому тяжёлое тело не грузится в канбан, но доступно в карточке и в FTS5-поиске.
- ✅ **Q-D2. История — в теле заявки, отдельной секцией.** Соответствует принципу «заявка = wiki-страница» и Obsidian-first: всё в одном файле, история видна в заметке. Секция размещается в конце файла; UI скрывает её при редактировании описания. При разрастании (сотни событий за годы) события старше N месяцев опционально выносятся в `tasks/.history/<ID>.md` (опц., не в MVP). Таблица `tasks_history` в индексе (§4.1) — отражение этой секции для быстрых запросов дашборда; источник правды — `.md`.
- ✅ **Q-D3. Единый FTS5-индекс для всех заявок (включая архив).** Соответствует решению VISION Q-3 (поиск по архиву включён по умолчанию). 10 000 архивных × 5 КБ ≈ 50 МБ — нормальный размер для FTS5; «холодный» индекс — преждевременная оптимизация. Видимость архива в выдаче регулируется фильтром `is_archived`, а не отдельным индексом.
